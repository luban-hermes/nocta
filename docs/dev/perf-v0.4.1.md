## 改了什么

### 1. 手机触摸（`components/Cards.tsx`、`components/ui/context-menu.tsx`）
- 新脚本 `work/pw/touch041.mjs`（仓库外）：Playwright `hasTouch / isMobile`（375 / 390 宽，1000 / 5000 档），用 CDP `Input.dispatchTouchEvent` 模拟真实手指：
  点按卡片 → 打开链接且不抬起、不发排序请求；长按 → 出右键菜单、不打开链接、不拖动；按住 320 ms 后移动 → 分类内拖动排序，DragOverlay 在 `<body>` 下，刷新后顺序保留；
  拖到屏幕底边停住 → 自动滚动跨过可视区，放下后服务端位置在首屏之外、刷新后保留；手指放在卡片上快速上滑 → 页面滚动、不抬起卡片，记录滑动期间帧率；点「+」添加站点 → 新卡片出现。
  （headless-shell 里 `Input.synthesizeScrollGesture` 根本不会滚动页面——空白处也不行——所以触摸滚动改用逐帧 touchMove。）
- v0.4.0 在这些场景下全部通过（TouchSensor `delay 200 / tolerance 7` + 长按 520 ms 出菜单的设计成立）。
- 找到并修复的问题：**Android Chrome 长按链接会派发原生 `contextmenu` 事件**，如果此时卡片已经被抬起（按住 >200 ms），菜单会打开而卡片仍处于拖动状态（DragOverlay 悬在手指下，松手后还可能发出排序请求）。
  现在两种卡片的 `onContextMenu` 都先 `cancelDrag()`（与长按菜单相同的取消方式），菜单打开时拖动一定结束。触摸脚本新增该场景（`android_contextmenu_during_drag`），v0.4.1 通过。

### 2. 星空减负（`components/Starfield.tsx`、`globals.css`、`components/ui/modal.tsx`）
- A/B 定位（1000 档、桌面、空闲 10 s、整个浏览器 CPU）：v0.4.0 空闲 ≈105%（1 核 = 100%）；关掉全部 CSS 动画只留星光闪烁 → 34%；只关星空画布 → 98%；只关天空 / 星云漂移 → 91%（但滚动 FPS 37 → 57）；再关品牌球的旋转环 → 41%。
  结论：开销不在画布本身，而在**无限循环的 CSS 动画**——只要有一个在跑，合成器就每秒出 60 帧，无 GPU 时每帧都要软件合成整屏并重新计算顶栏 / 弹窗玻璃的 backdrop blur。
- 做法：天空漂移（360 s 往返 24 px）、星云漂移（90 s 往返 12vw / 6vh）、品牌球的环与小卫星（6 s 一圈）不再用 CSS keyframes，而由星空的同一个 ~15 fps 时钟推进（同样的路径、周期和 ease-in-out 往返曲线）；
  漂移只在移动满 0.5 px（天空）/ 1 px（星云）时才写一次样式，所以实际每秒只有闪烁那十几帧。`html.sky-js` 存在时 CSS 动画关闭；没有 JS 或「减少动态效果」时仍由 CSS 负责（后者本来就静止）。
- 闪烁星 15–25 → 12–16 颗（只是最亮的那几颗，其余仍在静态层里），闪烁时钟 20 → 15 fps（闪烁周期 1.7–9 s，看不出差别）。
- 暂停：页面滚动中（最后一次 scroll 后 180 ms 内）、弹窗打开时（`Modal` 给 body 加 `x-modal-open`，背后有遮罩）、标签页隐藏时；暂停期间时钟不走，恢复后不会跳。浅色主题下只推进星云和品牌球。
- 外观：静态层（视场星 + 银河 + 暗带）完全没动；对比截图一致。

### 3. 备份流式导出（`lib/backup.ts`、`app/api/backup/download/route.ts`）
- `dumpChunks()`：按表（categories → sites → siteLinks → contents → monitors → checks → metrics）每次 500 行（按 id keyset 分页）生成 JSON 片段，再逐个读图标文件写 base64；输出字节与原来 `JSON.stringify(dump)` 完全相同的结构（同样的键和顺序），所以新旧备份互相可恢复。
- S3：`dumpChunks → gzip(level 9) → 临时文件 → PutObject(createReadStream, ContentLength)`，不需要新增 multipart 依赖，内存里从不出现整份 JSON 字符串或全部行；上传后删除临时目录。
- 新增 `GET /api/backup/download`（管理员）：同样的 `.json.gz`，边生成边下载（`Content-Disposition: attachment`）；设置 → 备份列表标题旁多了一个「下载」按钮（不需要配置 S3）。
- 恢复：仍是「下载对象 → 解压 → JSON.parse → 事务写入」（流式 JSON 解析需要新依赖，收益有限，没做）；恢复完成后会补齐排序间隔（见 6）。
- 回归：S3 模拟器（moto，:9200）往返——备份 → 改数据 → 恢复 → 站点 / 收藏逐字段签名一致；下载接口的 JSON 键顺序、版本、表行数与 `/api/items` 一致。

### 4. ⌘K 最慢一键（`components/CommandPalette.tsx`、`components/ui/modal.tsx`、`components/Cards.tsx`）
- 用 Event Timing 拆解 v0.4.1 中间版本的最慢一键：`processing` ≈ 0–1 ms，几乎全部是 **presentation delay**，而且总是每轮的**第一个按键**（打开面板后 1–3 ms 就按下）。trace 显示 VizCompositorThread 每帧 30–60 ms（软件合成），打开后的 ~400 ms 内有 7–8 帧：弹窗入场动画、遮罩淡入、结果行出现、每个图标陆续解码各一帧——第一个按键排在这些帧后面。
- 做法：
  - 结果行组件 memo 化；输入时只更新输入框，列表继续显示上一次的结果，直到新结果到达；快速连续输入时结果在停顿 110 ms 后才替换（打字的帧只重画输入框）；同一次打开内按查询缓存结果（删字立即出结果）。
  - 结果的图标先 `img.decode()`（最多等 150 ms）再显示行，图标随行在同一帧画出（`Tile eager` → `decoding=sync`），不再每到一个图标多一帧。
  - 空查询结果在鼠标移到搜索框、按下 ⌘ / Ctrl 时预取（含图标解码），面板第一帧就带结果。
  - 弹窗入场由 spring（420/32，约 0.5 s 才完全停下）改为 0.16 s 的 ease-out 补间，遮罩 0.25 → 0.16 s——起止状态不变，只是不再有长长的尾巴。
  - 星空在弹窗打开时暂停（见 2），弹窗打开期间浏览器 CPU 约 −60%。
- 收尾时又试了两种做法，都没有保留：
  1. 页面空闲时预取空查询 + 过期副本先显示再刷新（面板第一帧就带结果）：打字略快，但第一次打开面板的 INP 变慢（5000 档桌面 128 → 232 ms、手机 232 → 272 ms，第一帧要多画 24 行）。
  2. 只把结果替换的停顿从 110 ms 调到 180 ms：5000 档桌面每键 p50 104 → 72 ms、max 200 → 176 ms，但完整回归里「⌘K 跳到列表深处的收藏」连续两次失败（单独跑通过；110 ms 版本完整回归通过），所以撤回。
  两次的测量在 `work/perf/raw041/`（`cmdk-v041e-*`、`cmdk-v041f-*`、`v041f/`、`debounce180/`），代码差异在 `work/perf/cmdk-tweak-e.diff`、`cmdk-tweak-f.diff`（仓库外）。
- 之前还单独测过去掉弹窗入场动画（`cmdk-exp-noopenanim*`）：最慢一键 144–168 ms，与保留动画时在同一噪声范围内，所以入场动画不是首键慢的主要原因，外观保持不变。
- 结果见下表；与数据量无关的首键开销仍在，见「未达标」。

### 5. 首页不再为 ⌘K 下载全部列表（`app/api/search/route.ts`、`CommandPalette.tsx`、`NoctaApp.tsx`）
- 新增 `GET /api/search?q=&n=`：站点（名称 / 链接 / 描述）+ 收藏（标题 / 摘要 / 域名 / 标签）子串匹配（`instr(lower(...))`），按列表顺序（置顶 → 拖动顺序）返回精简行（id、标题、链接或域名、标签、图标 URL），无查询 24 条、有查询 60 条——与旧的本地搜索规则相同；监控列表本来就常驻，仍在本地匹配。
- 首页水合后只下载正在看的「站点导航」完整列表；**「收藏内容」完整列表只在打开该 tab（或从 ⌘K / 助手打开某条收藏）时下载**，鼠标移到 / 手指按到该 tab 时就开始预取；60 s 轮询在列表未下载时不会去下载它。
- 没做「按分类分别下载」：默认视图就是「全部」，站点完整列表本来就要；按分类缓存会让增删改、拖动都要同步多份列表，收益只在「首页一打开就点进某个分类」这一种情况。

### 6. 放下→保存 183 ms（`lib/sortgaps.ts`、`lib/scheduler.ts`、`app/api/reorder/route.ts`）
- 确认原因：种子数据（以及 v0.4.0 之前的旧数据、导入、旧备份恢复）的 `sort` 是连续整数，没有空隙；第一次拖动时 `/api/reorder` 找不到中间值，就整表重编号（5000 行一条 `UPDATE … ROW_NUMBER()`），并把**全部 5000 个新 sort 值**（≈129 KB）回传给浏览器重排。之后的拖动只写一行、回 44 字节。
  curl 实测（5000 档 v0.4.0）：第 1 次 86 ms / 129 KB，第 2、3 次 35 / 54 ms / 44 B；浏览器里第一次还要解析 129 KB 并重排整个列表，所以是 183 ms。
- 修法：`ensureSortGaps()` 在**启动时**和**恢复备份后**各检查一次（一条窗口函数查询：同一置顶分组内相邻 sort 差 < 2 的有没有），有就按现有顺序一次性把 sort 改成 1024 的倍数（站点、收藏各一条 UPDATE，在 SQLite 里是单语句事务）；顺序完全不变，数据量无关紧要（5000 行毫秒级），正常启动只做一次只读查询。拖动时的「没有空隙就整表重编号」保留为兜底（同一位置连续插入约 10 次才会用完间隔）。
- 不是 Prisma 迁移：迁移只会执行一次，而导入 / 恢复的数据随时可能没有空隙；启动检查对线上数据是只改 sort、不改顺序的幂等操作。

## 未达标 / 限制

- **⌘K 最慢一键仍未达到 150 ms**：v0.4.1 各档桌面 176–232 ms、手机 4× 112–208 ms（v0.4.0：桌面 256–360 ms、手机 184–376 ms）；p50 降到桌面 56–104 ms、手机 40–64 ms。最慢的总是每轮打开面板后立刻按下的第一个键，`processing` ≈ 0–1 ms，全部是 presentation delay：无 GPU 的沙盒里软件合成一帧弹窗（带 backdrop blur）就要 30–60 ms，第一个键排在打开动画的几帧后面。去掉入场动画后同样是 144–168 ms，所以没有为此改外观；在有 GPU 的真实设备上这一部分应当小得多（本机无法验证）。与数据量无关。
- **收藏内容 tab 第一次切换要下载完整列表**：首页不再预先下载收藏内容（鼠标移到 / 手指按到 tab 时开始预取），所以第一次切换比 v0.4.0 慢（5000 档手机 4× 398 → 744 ms，桌面 211 → 220 ms）；之后切换与 v0.4.0 相同。
- **没有按分类分别加载**：站点 / 收藏仍是整份列表（只是按需下载），原因见第 5 节。
- **恢复备份不是流式的**：导出已流式（S3 上传和直接下载都是），恢复仍是「下载 → 解压 → JSON.parse → 事务写入」，超大备份恢复时内存会有整份 JSON。
- **触摸只在模拟环境测过**：Playwright `hasTouch / isMobile` + CDP 触摸事件（Chromium 内核），没有在真实 iOS Safari / 真机上验证；iOS 的长按菜单、滚动惯性与 Chromium 不同。
- **手机空闲 CPU 仍约 97%**（4× 降速、无 GPU、整个浏览器所有进程）：比 v0.4.0 的 ~125% 低，但星光闪烁 + 软件合成在降速环境下仍占将近一核；桌面已降到 ~47%。真机有 GPU 合成时应明显更低（未验证）。
