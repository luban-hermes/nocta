# 夜航 Nocta v0.4.0 性能优化 — 开发记录

> 分支 `perf/v0.4.0`；依据：v0.3.1 分档性能报告（20/100/500/1000/2500/5000 条站点 + 同数量内容）。
> 目标：5000 站点 + 5000 内容时体验接近 100 条档（桌面可交互 <3 s、手机 4× <5 s、切 tab <1 s、⌘K 每键 <150 ms、拖起 <150 ms、放下→保存 <300 ms、添加 <1 s、无周期性卡顿、后台列表可用）。
> 约束：界面外观不变、不加说明文字；网格从左往右、短行不居中；悬停上浮不被裁切；数据库迁移对线上数据安全；备份格式可往返。

## 改了什么

### 1. 常驻 3D → 只在悬停卡片上（`globals.css`）
- `.sites` 去掉 `perspective`；`.site` 去掉 `transform-style:preserve-3d`；`.tile` / `.nm` / `.pin` 的 `translateZ` 只在 `.site.is-hot`（鼠标所在的那一张）下生效。
- `.site` 本身是 `overflow:hidden`，Chrome 会把它的 3D 子树拍平，所以静止时的 `translateZ` 在视觉上本来就不可见，只是每张卡多出 3 个合成层；悬停时的倾斜（`perspective(700px) rotateX/rotateY`）、图标放大、高光、阴影全部保留。
- 回归：静止状态下 `.site/.tile/.nm` 没有任何 transform / preserve-3d / will-change（v040.mjs 检查）。

### 2. 虚拟列表（`components/ui/virtual.tsx`）
- **站点网格 `VirtualGrid`**：按行窗口化。渲染出来的那几行仍放在同一个 `.sites` CSS grid 里（列数直接读 `grid-template-columns` 的实际轨道数），所以布局与 v0.3.1 完全一样：从左往右填、短行靠左、卡片不拉伸。上下用 padding 占位，页面高度 = 完整列表高度。
- **内容瀑布流 `VirtualMasonry`**：保持「第 i 张进第 i % 列」的阅读顺序；每列独立窗口化，卡片高度用 ResizeObserver 实测并缓存，没见过的卡片用平均高度估算。
- 列表都跟随页面滚动，没有内层滚动容器，也没有 `overflow / contain / content-visibility` 祖先 → 悬停上浮和阴影不会被裁（v040.mjs 用真鼠标检查首行、末行、左右边缘）。
- **拖拽**：`SortableContext` 仍拿到完整 id 列表，只有渲染出来的卡片注册为可放置目标；虚拟列表下 dnd-kit 改为持续测量（`MeasuringStrategy.Always`），拖到视口边缘时窗口自动滚动、新行挂载后立即可放。`DragOverlay` 仍 portal 到 `<body>`。
- **⌘K 跳转**：选中收藏 → 切到「收藏内容」并打开详情，同时把那张卡滚到视野里（先按估算位置滚，卡片测量后再校正，最后高亮一下）。
- 左侧分类栏仍是 sticky + 点击筛选（v0.3.1 的行为，没有改成分段长页）；切分类时网格整体重挂载，前 20 张照旧播放入场动画。

### 3. SSR 卡片直接可见（`Cards.tsx`）
- 站点卡 / 内容卡去掉 framer-motion 包装（原来 SSR 输出 `opacity:0`，要等 JS 水合完才看得见）。
- 入场改成纯 CSS（`.card-in`，0.4 s、每张错开 30 ms、16 px 上移，与原来一致），只给刚挂上的列表的前 20 张，滚动时新挂载的卡片不再播放。
- 卡片 `memo` 化，菜单 / 打开回调用稳定引用，拖拽和数据刷新时只重渲染真正变化的卡片。

### 4. 数据接口拆分（`lib/data.ts`、`/api/items`、`/api/sync`）
- 首页 SSR（`loadHomeData`）只带：设置开关、分类（含计数）、前 64 个站点、各列表总数、监控卡片、变更标记。5000 档首页 HTML 从 8.7 MB 降到 ~100 KB。
- 水合后立刻下载完整站点列表，空闲时下载收藏列表（`/api/items?kind=site|content`，gzip）。在完整列表到之前，分类计数用服务端计数，网格用总数撑出正确的页面高度。
- ⌘K 打开时确保两张列表都已下载，然后在本地搜（预先建好小写索引，`useDeferredValue`）。
- `/api/data` 保留（兼容），页面不再使用。

### 5. 增量刷新
- **压缩**：Next.js 的路由处理器会丢掉 `Content-Encoding` 头，也不会自己压缩 JSON。所以大列表用 `?z=1` 请求：服务端返回 gzip 字节（`application/octet-stream` + `x-nocta-z: gzip`），浏览器用原生 `DecompressionStream` 解压；不支持的浏览器自动拿普通 JSON（`lib/client.ts apiZ`、`lib/http.ts jsonz`）。5000 站点列表 ~2.6 MB → ~0.25 MB。
- **轮询**：每 60 s（监控页 15 s）只请求 `/api/sync?m=1`：三个变更标记（站点 = 条数 + 最新 updatedAt；内容同理；分类 = 内容摘要）+ 监控卡片（几 KB）。标记变了才重新下载那一张列表；分类变了（删除分类会把条目改成未分类）才三张都下。
- **本地更新**：右键菜单的置顶 / 移动分类 / 添加备用链接 / 重新抓图标 / 删除、添加对话框的新增与合并、拖拽排序，都直接用接口返回值更新本地列表，然后只记下新的变更标记，不再整表重下。抽屉里的编辑仍走 sync（只重下变了的那张表）。

### 6. 排序只写一行（`/api/reorder`）
- 新请求体 `{ kind, id, after, before }`（拖动后的左右邻居，~90 字节）。服务端把这一行的 `sort` 设到「after 与它在全局顺序中的下一项」之间（或 before 与上一项之间），间隔 1024。没有空隙时，用一条 `UPDATE … FROM (ROW_NUMBER() OVER …)` 把其他行重新编号一次（保持原顺序），新值随响应返回，前端直接套用。
- 置顶与未置顶之间的邻居不算（与原来「置顶永远在前」一致）。
- 旧的 `{ kind, ids }` 全量模式保留给分类排序；**去掉了 `.slice(0, 5000)`**，第 5001 个以后的 id 不再被静默丢弃。
- 新建站点 / 收藏的 sort 改为 ±1024 步长，给后续单行排序留空隙。不需要数据库迁移。

### 7. 图标
- `<img loading="lazy" decoding="async">`。
- URL 改为按文件：`/api/icon/f/<文件名>?v=<文件 mtime>`，`Cache-Control: private, max-age=31536000, immutable`。同一 host 的书签共用一个 `h_*` 文件 → 共用一个 URL 和一份浏览器缓存；文件被重写（重新抓取 / 上传 / 恢复备份）时版本号自动变化。旧的 `/api/icon/<site|content>/<id>` 仍可访问。
- 相似站点检测（添加时）的图标内容 hash 改为进程内缓存，不再每次读所有图标文件。

### 8. 瀑布流首帧列数
- 列数在第一次渲染时就从内容区宽度算出（`masonryCols`），手机上不再先渲染 3 列再改成 1 列、整组重挂载。

### 9. 后台「书签管理」
- `/api/admin/items?q=&sort=&dir=&offset=&limit=`：站点 + 内容在 SQL 里 `UNION ALL`，搜索（标题、网址、标签、分类名，与原来一致）、排序（默认 / 标题 / 类型 / 分类 / 日期，点表头切换）、分页都在服务端。
- 表格按行虚拟化，滚到哪页取哪页（每页 100 行）；搜索 200 ms 防抖。
- 每行只渲染一个静态的分类按钮（`SelectTrigger`，外观与原 Select 相同），全表共用一个下拉浮层（`SharedSelect`，键盘、点外部关闭等行为相同）。
- 后台首屏数据（`/api/admin/data`）只有分类、计数和最近 8 条收藏。

### P2
- 监控 24 h 可用率 / 心跳格 / 迷你图改为 SQL `GROUP BY monitorId, 桶` + 窗口函数取最近 30 个点，不再把 5740 行拉进 JS 逐个 filter。
- 多链接可达性探测只针对屏幕上停留 ≥1 s 的卡片（卡片挂载时登记、卸载时注销），5 分钟复查也只查登记中的链接；点击时的即时探测与故障切换不变。

## 验证结果（v0.3.1 → v0.4.0 分档复测）

环境与方法与 v0.3.1 报告相同：2 vCPU ARM64 / 8 GB 沙箱，Next.js standalone 生产构建；headless Chromium 无 GPU（软件光栅化，FPS 绝对值偏低，只看同环境对比）；桌面 1440×900 不降速，手机 375×812、DPR 2、CDP 4× CPU 降速；每档站点数 = 内容数（20 / 100 / 500 / 1000 / 2500 / 5000），同一随机种子生成，最大分类占 40%，约 60% 有图标、60% 内容有封面；20 个监控带 24 h 历史；全程管理员登录。

### 结论

**5000 站点 + 5000 内容时，各项体验已经回到（甚至好于）v0.3.1 的 100 条档。** 首页、切 tab、后台、拖拽、添加的耗时基本不再随数据量增长；滚动帧率从个位数回到 40+ fps；空闲时不再有周期性卡顿。

### 未达标 / 需要说明的项

1. **⌘K 每键 INP 最大值 200–256 ms（目标 150 ms）**：p50 在所有档位都 ≤ 208 ms、5000 档 136 / 96 ms，达标；超的是每轮 18 次按键里最慢的 1–2 次。这个最大值与数据量无关——v0.4.0 的 20 条档反而是 296 ms，100 档 320 ms——说明它来自打开面板后头几次按键的结果列表首次渲染 + 无 GPU 环境下的 presentation delay，而不是搜索本身（搜索是本地预建小写索引 + `useDeferredValue`）。v0.3.1 在 100 条时就已是 504 ms。后续可以把结果列表的首次挂载提前到面板打开动画期间来削掉这一下。
2. **站点页滚动 FPS 比 100 档低 15–23%**：41.8 vs 49.3 fps（桌面），42.8 vs 55.5（手机）。100 档整页只有 ~4 屏、图标早已全部解码；5000 档每滚过一个窗口块就要挂载一批新卡片和懒加载图标（rAF 每帧强制滚 60 px，比真人滚动快得多）。与 500 档持平、比 v0.3.1 的 5000 档高 8–18 倍；真机有 GPU 合成，绝对值会更高。
3. **手机 Lighthouse（模拟 4G + 4× CPU）1000 / 5000 档报 `NO_LCP`**：Lighthouse 没有记录到 LCP 候选，所以性能分、LCP、TBT、TTI 都算不出来（桌面预设正常：95 / 96 分）。同一次运行中 FCP 649 / 640 ms、Speed Index 2.2 / 2.5 s（v0.3.1 1000 档 9.1 s），页面确实在 0.6 s 左右就画出了内容。我们自己的 PerformanceObserver 在手机档也偶发拿不到 LCP（20、1000、2500 档；100、500、5000 档正常）。原因尚未查明，推测与首屏卡片的 CSS 入场动画（从透明开始）有关；不影响实际可见时间（首卡出现 0.4–0.67 s），但这是测量上的缺口。
4. **放下→保存 5000 档 183 ms**：达标，但比 1000 档（19 ms）、2500 档（40 ms）高；单次测量，没有拆解。可能原因：种子数据的 sort 是连续整数、没有空隙，第一次拖动会触发一次整列重编号（一条 `UPDATE … ROW_NUMBER()`，5000 行），之后的拖动只写一行。
5. **整体数据下载仍随数据量线性增长**：水合后一次性下载完整站点 + 内容列表（5000 档 gzip 后共 ~0.54 MB，各 ~140–180 ms），之后只有 17 KB 的 `/api/sync`。这是为了 ⌘K 全量本地搜索和分类计数；在下载完成前网格用服务端总数撑出高度，用户感知不到。50 并发下 `/api/items?kind=site` 5000 档 8.5 req/s——只有冷启动的页面才请求它。
6. **未测**：手机端触摸长按拖拽、悬停、添加（与 v0.3.1 报告一致）；备份流式导出与星空减负未做（P2，A/B 显示收益小，5000 档备份 0.7 s）。
